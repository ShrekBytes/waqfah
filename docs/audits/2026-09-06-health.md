# Maintainability/health audit — whole-codebase pass 2

- **Date:** 2026-09-06 · **Audited commit:** `981c522` (code identical to `0420241`, the pass-1 commit) · **Spec:** [issue #10](https://github.com/ShrekBytes/waqfah/issues/10)
- **Method:** exhaustive re-read of the 88 production files through the health lens (done alongside pass 1), full read of all 18 unit suites and 5 instrumented suites, doc-vs-code tracing of `docs/ARCHITECTURE.md`, `CONTEXT.md`, the four ADRs, and `AGENTS.md`, plus the gradle/CI files. Mechanical claims were re-verified by running them. No code was changed.
- **Verdict up front:** this codebase is in unusually good health. The docs match the code, the machine-and-adapter idiom is applied consistently, and the test suite pins behavior at exactly the seams the architecture claims exist. The findings below are notes, not wounds.

---

## 1. Doc accuracy — verified against the code

- **`docs/ARCHITECTURE.md`**: every load-bearing claim traced to code and confirmed — the core loop (MonitorSession poll rhythm, TriggerDecision rule ownership, service as adapter), the layer split (`data/local/core` destructive vs `data/local/appstate` preserving), the concurrency notes (mutation mutex, compare-and-set trigger claim, per-id download mutexes, double-checked Room handle cache), and the lifecycle rules (supervisor matrix, toggle-governs-detection-only, permission rows). The three "deliberate exceptions" to stateless screens are still exactly three (`ReadingViewModel`, the ReadingPorts consumer-owned port, `FeatureTourViewModel`).
- **`CONTEXT.md`** glossary: code naming conforms everywhere — MonitorSession, InterstitialSession, TriggerDecision, verdict, trigger stamp, ReadingSession, ReadingPorts, TourSession, verse selection, translation library. One vocabulary exception: the persisted column is `last_shown_at` (field `lastShownAt`), which uses the glossary's explicitly avoided name "last shown". It's a v1 schema legacy; renaming costs a migration for zero behavior change — **not worth doing on its own**, only if the schema ever changes again for a real reason.
- **ADRs 0001–0004**: all four match the code exactly — stamp-at-trigger-time inside `TriggerDecision` before the interstitial shows (verified in `decide()`), the toggle/detection boundary (the reading path never reads `appActive`, pinned by `ReadingRelevanceTest`), skip-persists-nothing (`dismiss()` writes nothing; only finishing reaches `onFinished`), and class-name interstitial identity via the constructor probe.
- **`AGENTS.md`**: both documented headless commands were run during this audit and are green (`:app:testDebugUnitTest`, `:app:assembleDebug`); `gradle/gradle-daemon-jvm.properties` exists as claimed; the CI workflow runs exactly what AGENTS.md implies plus an R8 release check.
- **`docs/agents/issue-tracker.md`** conventions were exercised for real during this audit (four specs published per its `gh` recipes) and work as written.

## 2. Seam quality

The architecture's central bet — pure "machines" with every impure edge arriving through the constructor — is applied consistently across seven machines (`TriggerDecision`, `MonitorSession`, `MonitorSupervisor`, `InterstitialSession`, `ReadingSession`, `TourSession`, `VerseSelection` + the pure `TranslationLibrary`), and each has an Android adapter of appropriate thickness (`AppMonitorService`, `TriggerActivity`, `MainActivity`, the ViewModels). No leaked state machine, no business logic in adapters, no seam bypassed.

One seam-observability note: `MonitorSessionTest`'s manual wall clock freezes while events are processed, so the suite cannot observe the class's only real-time-dependent defect (pass 1's P2-1 poll-window gap). If that fix lands, the natural regression test is to tie `nowWall` to the test scheduler and simulate processing latency — the test harness already supports it.

## 3. Test quality

Overall: **high**. Every suite tests external behavior at a machine seam — scripted event sequences with fake clocks, virtual time, seeded `Random`, inline fakes — and several carry regression references to the commits whose bugs they pin (`dd93b52`, `0d4b8f7`, `574651d` equivalents noted in test comments). `StringsParityTest` turns the AGENTS.md localization rule into a build failure; `TranslationCatalogTest` turns catalog invariants (one bundled per language, checksum shape, URL layout) into failures; `ReadingRelevanceTest` pins both sides of the render-signature decision.

Gaps, ranked — none blocking:

1. **The instrumented suite runs nowhere automated.** The five device tests include the Room migration validation and the translation-file gate — the two places where the JVM's `android.jar` stubs genuinely can't reach. CI has no emulator job, so a destructive-migration mistake ships unless someone remembers to run `connectedDebugAndroidTest` by hand. Suggest an emulator CI job, or an explicit pre-release checklist entry (pass 4's report will echo this).
2. `GoToSurahViewModel`'s combine/caching wiring is untested (only its pure filter is). Low risk — it's thin.
3. `ReadingSession` has no crash-policy test; there is currently no crash policy to test (pass 1's P3-4).
4. The `SettingsViewModel` toggle path is untested but is a thin adapter over the pinned supervisor matrix — acceptable.

## 4. Dead code and duplication

- **No dead production code found.** Every class, function, and resource traced to a use.
- Two unused drawables (`ic_rocket`, `ic_nagad`) exist only for commented-out rows in `SupportInfo.donations` — clearly deliberate future slots; harmless either way.
- Minor duplication, all below the rule-of-three threshold — noted so a third instance triggers extraction:
  1. the `AnimatedContent` fade+scale transition spec, identical in `MainScreen` and `FeatureTourOverlay`;
  2. the reading card's main ayah column vs `AyahPeekPage` (text styles already shared via `AyahText.kt`; the remainder differs deliberately);
  3. the `barColor` background-lerp logic in `ReadingCard`'s header and `WaqfahTabBar`;
  4. the optional-permission row branching (notification launcher vs settings deep-link) duplicated across `PermissionsScreen` and `OnboardPermissionsScreen`.

## 5. Deliberate debt (documented in-code, no action)

`checkOpNoThrow` (works on every supported API, commented), `overridePendingTransition` (API-guarded deprecation path), `getApplicationInfo(pkg, 0)` (default flags chosen deliberately), `LocalClipboardManager` (deprecated in newer Compose, cosmetic). The keep-rules file being all comments is *not* debt: `app/src/main/keepRules/` is AGP 9's standard rule location (the file's own header documents that AGP combines it), so the release build runs on AGP defaults plus library consumer rules — pass 4 verifies that's sufficient for the reflection touchpoints.

## 6. Toolchain exposure

The stack is deliberately bleeding-edge: AGP 9.3.2, compileSdk/targetSdk 37, Kotlin 2.2.10, Compose BOM 2026.08.00, and **Navigation 3 `1.1.6` (pre-stable)**. Nav3 is the only pre-stable runtime dependency; its API can shift under an upgrade. Mitigating factors, both already in place: navigation surface is small (one back stack, one `NavDisplay`, sealed `NavKey` destinations) and the serializer approach used is the officially documented pattern. Room 2.8.4 and Hilt 2.59.2 are stable releases.

## Recommendations (ranked; nothing was changed)

1. **Fix pass 1's P2-1** (window tiling) — the one correctness defect with user-visible reach — and pin it with a scheduler-driven wall clock as described in §2.
2. **Automate the instrumented suite** (emulator CI job or a release-checklist gate) — the migration safety net currently runs only when someone remembers it.
3. If `waqfah_app.db` schema changes again for any real reason, rename `last_shown_at` → the glossary's "trigger stamp" vocabulary in the same migration.
4. Nothing else. The correct move for this codebase is to leave its structure alone.

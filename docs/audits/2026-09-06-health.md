## 2. Findings not in the previous report

### P2-1 — A crashed `MonitorSession` loop leaves the foreground service running, showing an active-monitor notification while detection is dead

**Where:** `app/src/main/java/com/shrekbytes/waqfah/detection/AppMonitorService.kt:161` (the launch), `:59-64` (the handler that makes it silent).

`serviceScope.launch { monitorSession.run() }` has no completion or failure handling of its own. `run()`'s loop body calls three impure edges that can throw outside anyone's catch: the AppOps permission probe (`hasPermissions`, binder IPC), `resumedActivities(...)` (`UsageStatsManager.queryEvents`), and the preference read inside the decision (`preferences.first()` on DataStore). If any of them throws — or anything else in the loop does — the `CoroutineExceptionHandler` at `:61-64` logs and swallows, the loop coroutine simply completes, and the service keeps running as a foreground service with its "monitoring" notification. Detection is permanently off for the process lifetime while every visible signal says it is on. The session has no watchdog and nothing restarts it short of a service restart (toggle off/on, boot).

This is the same shape as pass 1's P3-4 (unhandled exceptions in one-shot scopes) but worse in effect: there the crash is loud, here it is silent *and persistent*. Probability is low (these calls rarely throw); the cost is the diagnosis kind — when it happens, the symptom ("monitoring is on but nothing triggers") gives no hint that the loop is dead, so each occurrence is disproportionately expensive to run down. That silent-divergence seam is what earns the P2, not frequency.

**Suggestion:** own the loop's lifetime at the launch site — e.g. `serviceScope.launch { try { monitorSession.run() } catch (t: Throwable) { Log.e(…); stopSelf() } }` so a dead session takes the (honest) notification down, or wrap `run()` in a restart-with-backoff if silent resurrection is preferred. Either way, the loop's death should never outlive unnoticed. (If P2-1 of pass 1 gets fixed, this pairs naturally: one retry wrapper.)

### P2-2 — `DatabaseModule` provides four DAOs that nothing injects (the "no dead code" claim's counterexample)

**Where:** `app/src/main/java/com/shrekbytes/waqfah/di/DatabaseModule.kt:29-32` (`provideSurahDao`, `provideVerseDao`) and `:43-47` (`provideMonitoredAppDao`, `provideReadVerseDao`).

Every consumer fetches its DAO from the database handle directly: `QuranRepository` injects `QuranDatabase` and calls `quranDatabase.surahDao()` / `verseDao()` inline (`QuranRepository.kt:14-43`); `MonitoredAppStateRepository` and `ReadingProgressRepository` inject `WaqfahAppDatabase` and call `monitoredAppDao()` / `readVerseDao()` themselves (`MonitoredAppStateRepository.kt:21`, `ReadingProgressRepository.kt:17`). A repo-wide search finds no injection site for any of the four DAO types — production or test. The bindings are live in the Hilt graph but serve nothing; `TranslationDao` correctly has no provider at all, which highlights the inconsistency.

This is small in lines but exactly the kind of map-rot the audit exists for: the DI module currently *documents a wiring that doesn't exist*, and the next agent reading `DatabaseModule` will assume DAO injection is the idiom here.

**Suggestion:** delete the four providers (one-line change, zero behavior risk — the green build is the proof they're unrequested), or move `QuranRepository`/the appstate repositories to constructor-inject the DAOs to match them. Pick one idiom; today the module and the repositories disagree.

### P3-1 — `ARCHITECTURE.md`'s trigger-rule list omits the INACTIVE check (pass 1's handed-off note, recorded)

**Where:** `docs/ARCHITECTURE.md:15-32` vs `app/src/main/java/com/shrekbytes/waqfah/detection/TriggerDecision.kt:212`.

Pass 1 explicitly handed "doc-vs-code rule-order trivia (e.g. the INACTIVE rule's position relative to switch-back)" to this pass; the first health report never picked it up. Recording it now: `decide()` checks `!triggerPrefs.appActive → INACTIVE` between indirect-entry and switch-back; the map's seven-rule list has no INACTIVE step. The check is a defensive re-read of persisted truth (the gate should already have paused the loop), and since both INACTIVE and SWITCH_BACK are non-triggering ignores, the position is behavior-neutral — but the map's list is incomplete, and a reader matching code against it will see an undocumented branch.

**Suggestion:** one doc line in the rule list ("a defensive re-check of the persisted toggle, before switch-back, whose only effect is the logged reason") or an explicit note that the list omits it. Doc-only; no code change.

### P3-2 — Two API surfaces exist only for tests: `MonitoredAppState.add`/`remove`, and `TourSession.back()`'s result

**Where:** `app/src/main/java/com/shrekbytes/waqfah/data/monitoredapp/MonitoredAppState.kt:22-23`; `app/src/main/java/com/shrekbytes/waqfah/ui/tour/TourSession.kt:13,126`.

Neither has a production caller: all features mutate monitored-app membership through `toggle` (`AppsViewModel.toggle`, onboarding's shared `AppsViewModel`), and `add`/`remove` are invoked only by `MonitoredAppStateRepositoryInstrumentedTest`. Likewise the overlay's `BackHandler { tourSession.back() }` (`FeatureTourOverlay.kt:112`) discards the returned `TourBackResult`; only `TourSessionTest` asserts on it. This is not dead weight to delete blindly — the instrumented suite exercises the fine-grained membership ops and the result type *names* the back-ordering contract — but the domain surface is one size larger than the domain. A maintainer reading the `MonitoredAppState` interface would reasonably assume `add`/`remove` are used somewhere.

**Suggestion:** leave if deliberate (test seams are legitimate users), but say so: a one-line comment on each ("production goes through toggle; these are the membership primitives the instrumented suite exercises directly") costs nothing and prevents both a wrong "cleanup" and a wrong new usage.

### P3-3 — Glossary vocabulary drift in comments and one opaque key

**Where:** `TriggerActivity.kt:48,51,180` ("target app" — the avoid-list term for *monitored app*), `AppMonitorService.kt:76` ("share targets" — the avoid-list term under *indirect entry*), `ResumedActivityReaderTest.kt:10` ("buried-retry check") and `TriggerActivity.kt:205` (`STATE_REASSERT_USED = "waqfah.buriedRetryUsed"` — "retry" is the avoid-vocabulary for the re-assert).

Cosmetic — worth touching only when those files are edited anyway. If touched: rename the Bundle key in the same commit as any other change to that file (instance state doesn't survive an app update, so the rename is free).

### P3-4 — A fifth duplication: the shared press-highlight rule exists twice in `SettingsControls.kt`

**Where:** `app/src/main/java/com/shrekbytes/waqfah/ui/components/SettingsControls.kt:140-152` (`Modifier.rowHighlight`) vs `:265-278` (`SettingsNavRow`'s inline highlight).

Same rule in both: `line.copy(alpha = 0.6f)` highlight, tween 60 ms in / 220 ms out, no indication. `rowHighlight` was extracted as "the one shared treatment for flat list rows" (its own doc comment), and `SettingsNavRow` predates or ignores it. Below rule-of-three today — but a third variant would be the trigger the first report's §4 itself defined, and this one is closer to three than any pair it listed.

**Suggestion:** have `SettingsNavRow` use `rowHighlight` (it differs only in padding/chevron), or delete the extension and inline it everywhere, so the "one shared treatment" claim in the doc comment is true.

### P3-5 — Clock-idiom inconsistency in the data layer

**Where:** `app/src/main/java/com/shrekbytes/waqfah/data/repository/ReadingProgressRepository.kt:27` vs `MonitoredAppStateRepository.kt:18`.

`markRead` stamps `System.currentTimeMillis()` directly, while the sibling repository that owns trigger stamps takes `@Named("wallClock")` from AppModule and is constructed with a controllable clock in its instrumented test (`MonitoredAppStateRepositoryInstrumentedTest.kt:41`). One repo treats wall time as an injectable seam, the other hardcodes it. No behavioral issue today (`read_at` is not pinned by any test), but the idiom split is the kind of thing that confuses the next clock-sensitive feature.

**Suggestion:** either inject `@Named("wallClock")` here too, or accept the split deliberately with a one-line comment on `markRead`. Trivial either way; only worth doing when the file is next open.

## 5. Recommendations (ranked; nothing was changed by this pass)

1. **P2-1:** give `MonitorSession.run()`'s launch site a failure owner (`stopSelf()` or restart-with-backoff) so a dead loop can't hide behind a live notification. Pair it with pass 1's P2-1 window fix and the scheduler-driven wall-clock test the first report sketched — the harness already supports it.
2. **P2-2:** delete the four unused DAO providers in `DatabaseModule` (or move the repositories to DAO injection — pick one idiom). One commit, zero behavior change, restores the "no dead code" truth.
3. **Automate the instrumented suite** (emulator CI job or an explicit release gate) — unchanged from the first report, still the highest-value process fix.
4. **P3-2/P3-3:** two one-line comments on the test-only membership ops and a vocabulary pass over the four flagged comments when next touching those files. Doc-only.
5. If `waqfah_app.db` schema changes again for a real reason, rename `last_shown_at` in the same migration — unchanged from the first report.
6. Nothing else. Both passes now agree on the headline: the correct move for this codebase's structure is to leave it alone.

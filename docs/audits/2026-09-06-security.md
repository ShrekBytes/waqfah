- **Threat model** (per the spec, proportionate to a personal-use digital-wellbeing app): untrusted translation files, accidental over-exposure of components/data, and gap between privacy claims and code — not a targeted adversary.

## Findings

### P2-S1 — Cloud backup ships user data off-device while the shipped policy says it never leaves the device

**Where:** `app/src/main/AndroidManifest.xml:38` (`android:allowBackup="true"`), `app/src/main/res/xml/backup_rules.xml`, `app/src/main/res/xml/data_extraction_rules.xml` vs `app/src/main/res/values/strings.xml:208`

The backup rules keep everything except `file/translations`: the Room DB `waqfah_app.db` (monitored package names, per-app last-triggered timestamps — the ADR-0001 stamps — and full read-verse history with timestamps) and the `waqfah_settings` DataStore (all preferences) ride in Android cloud backup and device-to-device transfer. The in-app policy states, unconditionally: "Everything Waqfah knows lives in its own local storage on your phone … **None of it ever leaves your device.**" and README:37 says "Monitored apps, reading progress, and preferences stay on the device." Under any signed-in Android 9+ device, the OS periodically sends exactly that data to the user's Google account (or a transfer cable). The XML comments show this is a deliberate, documented trade ("keep user data … skip the re-downloadable translation databases"), and the destination is the user's own account — so the headline claims ("collects nothing and sends nothing anywhere", "no tracking", nothing reaches the developer) still hold. But the absolute sentence in the shipped policy is false under backup, and this is exactly the claim-vs-code gap the audit exists to catch.

**Fix (either side):** soften the policy/README wording — e.g. "…never leaves your device except Android's standard device backup, which stores it in *your* Google account" — or tighten the backup policy to exclude `database/` and DataStore too if the maintainer wants the strict reading of the claim. Wording is the cheaper fix and keeps the backup convenience.

### P3-S2 — Release-build logs name the user's app activity in logcat

**Where:** `app/src/main/java/com/shrekbytes/waqfah/detection/AppMonitorService.kt:197-212` (`handleVerdict`) and `:252` (launch-failure `Log.e` with the package name)

Every trigger and most ignore reasons log the observed package and class name (`Log.d(TAG, "Triggering reading screen for $packageName …")` and similar for call/interstitial-return/call-grace/indirect/claim-rejected skips), plus the launch-failure handler at line 252. These are compiled into release builds — no `BuildConfig.DEBUG` guard exists, and R8 runs with default rules only (no project proguard file, confirmed under `app/`), which does **not** strip `Log.d`/`Log.e`. Logcat is device-local and unreadable by other apps (adb or root required), so this does **not** contradict "no tracking" — nothing leaves the device. But the in-app policy's "never records your browsing or app history anywhere" (`strings.xml:210`) is strained by a debug ring buffer that records exactly which app you opened and when, recoverable over adb.

**Suggestion:** guard the verdict-detail logs behind `BuildConfig.DEBUG` (or `Log.isLoggable`), keeping error-level logs unguarded (or dropping the package name from the line-252 message). One-line change per call site; no behavior impact.

### P3-S3 — Download integrity verification fails open when a catalog entry lacks a pin

**Where:** `app/src/main/java/com/shrekbytes/waqfah/data/repository/TranslationRepository.kt:258`

`verifyChecksum` begins `val expected = meta.checksumSha256 ?: return` — a downloadable catalog entry *without* a pinned checksum downloads and is installed with **no byte verification** (only the generic SQLite gate: magic bytes, read-only open, `user_version`, schema probe — which a malicious but well-formed `.db` passes). Today this is unreachable: every downloadable entry in `TranslationCatalog` (`data/model/TranslationModels.kt:32-41`) pins a checksum, and `TranslationCatalogTest.downloadableEntries_pinWellFormedSha256Checksums` enforces non-null well-formed pins. But that guard lives in a test, not in the type or the code path — a future catalog row added without updating the test's expectations silently reintroduces an unverified download of scripture. The https scheme of `downloadUrl` is likewise enforced only by the test (`downloadUrls_pointAtExpectedRepoPath`); the platform's default no-cleartext policy (targetSdk 37) is the backstop there.

**Suggestion:** fail closed in `verifyChecksum` — for non-bundled entries, a missing pin should throw (`error("… has no pinned checksum")`) instead of returning. Alternatively encode bundled-vs-downloadable in the type so a downloadable entry cannot exist without a checksum.

### P3-S4 — Download body is written unbounded before the checksum check runs

**Where:** `app/src/main/java/com/shrekbytes/waqfah/data/repository/TranslationRepository.kt:208-237`

The download loop writes the response body to internal storage until EOF (`while (true)` at line 219) with no cap on `contentLengthLong` or on `bytesRead`; the SHA-256 verification (line 237) and SQLite validation run only after the full body has landed in `filesDir/translations/…tmp`. A hostile or compromised CDN edge serving the pinned URL could stream arbitrarily large bytes and fill the device's internal storage before rejection. Reachability requires the same trust-anchor compromise as P3-S5, so this is hardening, not exposure — with valid pins the size of a passing body is fixed anyway.

**Suggestion:** reject at stream start when `contentLengthLong` exceeds a sane bound (translations are a few MB), and abort the loop when `bytesRead` crosses it.

### P3-S5 (noted, no action) — Supply-chain trust anchor for translations is the maintainer's own repo

The integrity chain for downloaded translations is: SHA-256 pinned in `TranslationCatalog` (in this repo) → verified before the download's atomic rename (`TranslationRepository.kt:236-243`, validated file first, then checksum, then rename, tmp cleanup on failure). The pins point at `https://raw.githubusercontent.com/ShrekBytes/waqfah-translations/…`. So the trust root is the maintainer's translation repo *plus* this repo's catalog staying in sync (the catalog's MAINTENANCE comment documents the regeneration duty; `TranslationCatalogTest` enforces pin well-formedness). A compromise of the translations repo alone is caught by the pins; a compromise of both repos (or a careless checksum regeneration over a changed file) could ship a hostile `.db`. Residual exposure is then the platform SQLite parser (pre-auth on open) — patched by Android itself, and the app only ever issues one parameterized read against the file. This is the right design at this scale; the note exists so the trust chain is written down: **the checksums in `data/model/TranslationModels.kt` are the security boundary for downloads.**

## Egress inventory (the "no other network requests" claim, verified)

Exactly one code path reaches the network in the entire app:

- `TranslationRepository.downloadOverNetwork` (`TranslationRepository.kt:192-251`) — `HttpURLConnection` GET to `https://raw.githubusercontent.com/ShrekBytes/waqfah-translations/main/<lang>/<id>.db`, TLS by scheme (and cleartext blocked platform-wide at targetSdk 37), no credentials, no headers beyond `Accept`, only fired by an explicit user action (Download/Retry rows in TranslationsScreen). Content is validated (magic bytes → read-only SQLite open → `user_version` gate → schema probe → checksum) **before** the tmp file is renamed into place; a failed download leaves nothing behind.

User-initiated, non-app egress (nothing the app sends; payloads are hardcoded in `SupportInfo.kt`/`GratitudeScreen.kt`):

- About screen: `ACTION_VIEW` to `https://github.com/ShrekBytes/waqfah`; `ACTION_SENDTO mailto:shrekbytes@duck.com` (`ui/about/AboutScreen.kt:82,88`).
- Gratitude screen: contributor profile links (github.com/shrekbytes, github.com/emptymahbob, github.com/Mr-Explorer142) and source credits (`https://qul.tarteel.ai/`, `https://tanzil.net/`) via `ACTION_VIEW`.
- Settings deep-links (`PermissionsRepository.kt:44-64`): system settings screens for this app only (usage access, overlay, notification, battery, app-details) — no data attached beyond the own package name.
- `DonateScreen` writes the donation number to the clipboard on tap — a user-initiated write, never a read.

That is all. The `<queries>` probe intents (`ACTION_SEND`/`ACTION_VIEW` with `probe.waqfah.local` URIs, `AppMonitorService.kt:218-227`) are PackageManager *queries* — nothing is ever started, nothing leaves the device. No analytics, no crash reporting, no ads, no accounts — confirmed at the dependency level too: every entry in `gradle/libs.versions.toml` is androidx/JetBrains/Google first-party (Compose, Room, Hilt, DataStore, Navigation3, kotlinx), none carrying telemetry or network behavior in the way the app uses them.

## Explicitly checked and found sound

- **Component surface:** only `MainActivity` is `exported="true"` (launcher, required; its `onCreate` never reads intent data/extras, so external launches carry no attack surface). `TriggerActivity` (manifest:64), `AppMonitorService` (72), and `BootReceiver` (99) are all `exported="false"`; the receiver relies on `BOOT_COMPLETED` being a protected broadcast (documented in-manifest). No content providers, no custom permissions, no deep links, no `PendingIntent`s anywhere in production code. `TriggerActivity` null-checks its extra and finishes when absent.
- **Package visibility / `<queries>`:** the single MAIN/LAUNCHER declaration (manifest:29-34) is what makes the indirect-entry probes work on API 30+ — visibility is per-package, so every launchable app (nearly all share-target holders) is visible to the SEND/VIEW `queryIntentActivities` probes in `AppMonitorService`. The app-picker's launcher query is covered by the same declaration. (Residual blind spot: launch-less packages with share targets — behavior-only, and fail-safe: fewer suppressions, never more.)
- **Overlay + background starts:** `SYSTEM_ALERT_WINDOW` exists solely to exempt the app's *own* `TriggerActivity` launches from background-start restrictions; other apps cannot invoke it (`exported="false"`, no intent filter). The re-assert path is self-launched and once-only (bundle-pinned).
- **Usage-stats handling (the most sensitive capability):** foreground observations live in `TriggerDecision`/`MonitorSession` memory only; `claimTrigger` is a compare-and-set Room update that persists only `last_shown_at` per monitored package. Nothing about *which* apps were observed, when, or their screens is ever written to disk beyond that stamp — and no release build writes it to any sink that leaves the device (logcat aside, P3-S2).
- **Untrusted-file parsing:** validation runs before the file lands (magic header → `OPEN_READONLY` open → version gate (0 or expected) → schema probe via a static query → checksum), the read path is one parameterized `SELECT … LIMIT 1` through Room, and all DAO/Repository SQL in the app is static or bound — the only `execSQL` is the hand-written migration's fixed DDL with parameterized inserts (`AppStateMigrations.kt`). No string-built SQL anywhere: no injection surface. Room's first open of a downloaded file may write `room_master_table` into it (internal storage, app-private) — benign.
- **Storage inventory (what lands where):** `filesDir/translations/…db` (downloaded/bundled translations; tmp files same dir, cleaned on failure), internal Room `waqfah_app.db` (monitored apps + stamps, read verses), internal DataStore `waqfah_settings` (preferences incl. `app_active`), `databases/quran_core.db` (asset copy). Nothing external, no world-readable modes, no cache-dir surprises. Backup policy is the one off-device path — P2-S1.
- **Permissions:** all seven declared permissions traced to concrete use (internet = downloads; notifications = FGS notification visibility on 13+; usage stats = detection via AppOp + settings deep-link; boot = monitor restart; overlay + the two FGS permissions = the interstitial service). Nothing declared-but-unused; no dangerous runtime permission beyond `POST_NOTIFICATIONS`; battery exemption is deliberately *not* requested (deep-link to app details instead) — matching the in-app permission catalog word for word.
- **FGS compliance:** `specialUse` type declared with the required subtype property; the service self-stops when usage/overlay permissions are revoked (30 s heartbeat in `MonitorSession`, re-checks on resume/boot).
- **Receivers:** the screen-state receiver is registered `RECEIVER_NOT_EXPORTED` (`AppMonitorService.kt:148-156`) and listens only to protected system broadcasts; `BootReceiver` acts only on the protected `BOOT_COMPLETED`.
- **Crypto/surfaces:** no WebView, no JS bridge, no `Random` in security-sensitive roles (only verse selection via injected `Random`), no crypto beyond streaming SHA-256, no microphone/camera/location, no accessibility services, no clipboard reads; call detection reads only the public `AudioManager` routing mode — never call content or state.
- **Build surface:** targetSdk 37 / minSdk 28; release has R8 optimization enabled with default rules; `debuggable` defaults off; no custom proguard rules; `debugImplementation` artifacts (test manifest, tooling) cannot reach release. No network security config — the platform default (cleartext forbidden) is the effective policy, and the only URL is https.

# Security/privacy audit — whole-codebase pass 3

- **Date:** 2026-09-06 · **Audited commit:** `62b0998` (code identical to `0420241`) · **Spec:** [issue #11](https://github.com/ShrekBytes/waqfah/issues/11)
- **Threat model** (per the spec, proportionate to a personal-use digital-wellbeing app): untrusted translation files, accidental over-exposure of components/data, and gap between privacy claims and code — not a targeted adversary.
- **Method:** every production file re-read through the security lens, with deep dives on the translation download/parse path, the component surface, storage/backup, logging, and a full egress inventory. No code was changed.
- **Verdict up front:** the privacy claims are load-bearing. The app's entire network surface is one code path, the component surface is closed, no third-party code with network/telemetry behavior exists, and the most sensitive capability (usage-stats reading) never leaves memory. Two P3 hardening notes below; nothing blocking.

## Findings

### P3-S1 — Release-build logs name the user's app activity in logcat

**Where:** `app/src/main/java/com/shrekbytes/waqfah/detection/AppMonitorService.kt:197-212` (`handleVerdict`)

Every trigger and most ignore reasons log the observed package and class name (`Log.d(TAG, "Triggering reading screen for $packageName …")` and similar for call/indirect/interstitial-return/cooldown skips). These logs are compiled into release builds — no `BuildConfig.DEBUG` guard and no R8 log-stripping rule exists. Logcat is device-local and unreadable by other apps (adb or root required), so this does **not** contradict "no tracking" — nothing leaves the device. But the in-app policy's "never records your … app history anywhere" is strained by a debug ring buffer that records exactly which app you opened and when, recoverable over adb.

**Suggestion:** guard the verdict-detail logs behind `BuildConfig.DEBUG` (or `Log.isLoggable`), keeping the error-level logs unguarded. One-line change per call site; no behavior impact.

### P3-S2 (noted, no action) — Supply-chain trust anchor for translations is the maintainer's own repo

The integrity chain for downloaded translations is: SHA-256 pinned in `TranslationCatalog` (in this repo) → verified before the download's atomic rename. The pins point at `https://raw.githubusercontent.com/ShrekBytes/waqfah-translations/…`. So the trust root is the maintainer's translation repo *plus* this repo's catalog staying in sync (the catalog's MAINTENANCE comment documents the regeneration duty, and `TranslationCatalogTest` enforces checksum well-formedness). A compromise of the translations repo alone is caught by the pins; a compromise of both repos (or a careless checksum regeneration over a changed file) could ship a hostile `.db`. Residual exposure is then the platform SQLite parser (pre-auth on open) — patched by Android itself, and the app only ever issues one parameterized read against the file. This is the right design at this scale; the note exists so the trust chain is written down: **the checksums in `data/model/TranslationModels.kt` are the security boundary for downloads.**

## Egress inventory (the "no other network requests" claim, verified)

Exactly one code path reaches the network in the entire app:

- `TranslationRepository.downloadOverNetwork` — `HttpURLConnection` GET to `https://raw.githubusercontent.com/ShrekBytes/waqfah-translations/main/<lang>/<id>.db`, TLS by scheme, no credentials, no headers beyond `Accept`, only fired by an explicit user action (Download/Retry rows). Content is validated (magic bytes, read-only SQLite open, `user_version` gate, schema probe) and SHA-256-verified **before** the tmp file is renamed into place; a failed download leaves nothing behind.

That is all. The `<queries>` probe intents (`ACTION_SEND`/`ACTION_VIEW` with `probe.waqfah.local` URIs) are PackageManager *queries* — nothing is ever started, nothing leaves the device. `launchExternal` opens user-initiated browser/mail links (About/Gratitude rows) with the URL itself as the only payload. No analytics, no crash reporting, no ads, no accounts — confirmed at the dependency level too: every entry in `gradle/libs.versions.toml` is androidx/JetBrains/Google first-party, none of which carry telemetry or network behavior in the way the app uses them.

## Explicitly checked and found sound

- **Component surface:** only `MainActivity` is `exported="true"` (launcher, required). `TriggerActivity`, `AppMonitorService`, and `BootReceiver` are all `exported="false"`; the receiver relies on `BOOT_COMPLETED` being a protected broadcast (documented in-manifest). No content providers, no custom permissions, no deep links, no `PendingIntent`s anywhere.
- **Overlay + background starts:** `SYSTEM_ALERT_WINDOW` exists solely to exempt the app's *own* `TriggerActivity` launches from background-start restrictions; other apps cannot invoke it (`exported="false"`, not exported via any intent filter).
- **Usage-stats handling (the most sensitive capability):** foreground observations live in `TriggerDecision`/`MonitorSession` memory only; the sole persisted trace of detection is the per-app trigger stamp the cooldown requires (ADR-0001). Nothing about *which* apps were observed, when, or their screens is ever written to disk — the claim "never records your browsing or app history anywhere" holds for persistent storage.
- **Untrusted-file parsing:** validation runs before the file lands (magic header → `OPEN_READONLY` open → version gate (0 or expected) → schema probe via a static query → checksum), the read path is one parameterized `SELECT … LIMIT 1` through Room, and all DAO/Repository SQL in the app is static — no string-built SQL anywhere, so no injection surface.
- **Storage:** everything lives in internal storage (`filesDir`, internal Room/DataStore); nothing touches external storage or world-readable modes. Backup policy is deliberate and documented in both rules files (Android 9–11 and 12+): user data (monitored apps, reading progress, preferences) is kept; re-downloadable translation DBs are excluded. Backups go to the user's own cloud/device-transfer target — the monitored-app list riding along in a personal backup is a fair, user-owned trade, stated in the XML comments.
- **Permissions:** each of the seven declared permissions traced to a concrete use (internet = downloads; notifications = visibility of the monitor notification; usage stats = detection via AppOp + settings deep-link; boot = monitor restart; overlay + FGS = the interstitial and its service). Nothing declared-but-unused, and no dangerous runtime permission beyond `POST_NOTIFICATIONS` — matching the in-app permission catalog and rationale screens word for word.
- **FGS compliance:** `specialUse` type declared with the required subtype property; the service self-stops when permissions are revoked.
- **Crypto/surfaces:** no WebView, no JS bridge, no `Random` in security-sensitive roles (only verse selection), no crypto beyond streaming SHA-256, no microphone/camera/location, and call detection reads only the public audio-routing mode — never call content or state.
- **README claim "everything works offline except the explicit translation downloads":** confirmed — two translations ship bundled, so even downloads are fully optional.
